# Project detail content uses one interface with optional sections, not generic blocks

Each Project's detail page shows a different mix of content sections (metrics, timeline, challenges, solutions, achievements, tech stack, skills) because no two projects tell their story the same way. We considered a generic block system — an array of `{ type, payload }` sections a project could freely compose from — which would let any future project define arbitrary new section types without touching a shared interface. We chose instead a single `ProjectItem` interface in `globalInterfaces.ts` where every content section is optional, and the detail page conditionally renders whichever sections a given project's JSON includes. This keeps every field typed (no `any`/`unknown` payloads), matches this repo's existing convention of one typed interface per JSON data shape, and avoids building flexibility nothing has needed yet. The cost: a genuinely novel section type for a future project requires extending the shared interface rather than composing one from existing primitives.
